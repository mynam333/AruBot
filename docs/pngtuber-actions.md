# PNGTuber Response Actions

Use `${pngtuber::happy::5}` in a normal/point command response, donation rule response, or roulette result action to show a locally saved reaction for five seconds. `${pngtuber::happy}` uses that reaction's locally saved default duration. `${짚톡::happy::5}` is an alias.

- The reference is a saved reaction ID or unique name, at most 80 characters. URLs, filesystem paths, control characters, and nested variables are rejected. Images stay local; the server never loads an asset from the token.
- An explicit duration must be a finite decimal number from 0.1 through 300 seconds. Empty, malformed, and out-of-range values fail; they are not clamped or replaced with the default.
- Existing command prices and donation handling still apply. This action introduces no price, point deduction, or refund system. Blueprint no-cost replay context is preserved.
- The local program must be online and advertise `capabilities.pngtuber === true`. Older clients fail with `pngtuber_local_agent_upgrade_required`. The server queues `pngtuber.show` through the existing automation admission/budget checks, with `payload.reactionId`, optional numeric `payload.durationSec`, provenance, and numeric `payload.expiresAt = Date.now() + 60000`. Expiry limits when a queued job may begin, not its playback duration. A non-capable client claiming this shared queue never receives the reaction job; the server records a failed job with the same upgrade error.
- Local main passes the job ID to the local service for idempotent acknowledgement. The service resolves IDs/unique names and applies its saved default duration, 32-preset limit, 20-entry reaction queue, and queue/replace setting. Missing/ambiguous presets, disabled service, queue rejection, and expiry must fail locally instead of acknowledging success.
- A successful server enqueue means queued, not confirmed playback. Invalid server tokens, offline agents, and failed enqueue return failed action results. Normal command responses include a failure notice; donation and roulette renderers collect action errors. Tokens themselves are removed from authored chat responses, including invalid explicit durations.
- Command reactions are authorized against exact saved-template tokens and their occurrence counts, never the rendered viewer name, arguments, memo, or lookup data. Rendered input cannot change the preset or duration or add more executions of a saved token. Donation and roulette actions are planned from the saved template before viewer/donor data is substituted. A token in a donor message does not authorize an action. Mixed blueprint/reaction tokens execute in their authored order.
- Existing blueprint command execution supports these response variables without a new node. Simulation does not enqueue. Connected tests use the existing online check and `maxAttempts: 1`, carry `testMode: 'connected'`, and remain no-cost. Timed display is not awaited by the server.
- Command and donation variable help share the `/api/bot/variables` catalog. Managers need `actions:write` to bind the effect, in addition to the page's normal edit permission.

Focused tests use mocks and extracted server functions, never a running server, live chat, OBS, or a local program instance.
