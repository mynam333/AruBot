# 연결 없는 아루봇 계정 정리

## 연결 해제

CHZZK·CIME·YouTube 연결 해제 후, 서버는 계정 행을 잠근 트랜잭션 안에서 남은
플랫폼 연결을 다시 검사한다. 마지막 연결이 제거되면 계정 소유 데이터와 세션을
정리하고 현재 브라우저를 로그아웃한다. 다른 플랫폼 연결이 있으면 계정은 유지한다.
DB 조회 실패는 연결이 없는 것으로 처리하지 않는다.

토큰 갱신은 읽었던 인증정보가 여전히 같은 경우에만 저장한다. 연결 해제 후 도착한
오래된 갱신 응답은 토큰을 다시 만들 수 없다. YouTube 인증 만료 정리도 읽었던
토큰·동의 시점·로그인 시점을 확인하여 새로 연결한 계정을 삭제하지 않는다.

`platform_accounts` 외에 구형 토큰 또는 YouTube 스트리머 채널 등록이 남아 있으면
실제 연결이 없는지 단정할 수 없으므로 자동 삭제하지 않는다. 정리 결과의
`legacy_connection`으로 집계한다. 기존 로그인 데이터가 부족한 사용자나
중앙 YouTube 봇 기반 사용자도 이 예외로 보호한다.

계정의 예전 플랫폼 ID·닉네임은 다른 사용자에게 다시 연결되었을 수 있다.
자동 정리는 `owner_user_id`, `account_user_id`, 내부 `user:<계정 ID>` 및
아루봇 시청자 UUID 같은 소유권이 명확한 키만 사용한다. 과거 플랫폼 ID로만
저장되어 소유자를 증명할 수 없는 데이터는 자동 삭제하지 않는다.

## 기존 계정 일괄 정리

운영 서버의 프로젝트 폴더에서 DB 환경변수를 읽어 실행한다.

```powershell
node scripts/cleanup-unlinked-accounts.js --dry-run
node scripts/cleanup-unlinked-accounts.js --apply
```

인자가 없으면 조회만 수행한다. 신규 인증 처리 보호를 위해 생성 후 1시간이 지난
계정만 일괄 작업 대상이다. 마지막 연결의 명시적 해제에는 이 유예 시간이 없다.
각 계정은 삭제 직전에 연결 상태를 다시 검사한다. 계정 DB 삭제 트랜잭션 안에서
오류가 나면 그 계정을 롤백한다. 삭제가 커밋된 뒤 로컬 파일 정리에 실패한 경우는
계정 삭제를 되돌리지 않는다. 두 실패를 구분해 집계하며 명령은 실패 상태로 종료한다.
정리 대상 조회가 되지 않으면 삭제를 실행하지 않는다.

기존 개인정보 보관기간 작업이 켜져 있으면 서버 시작 후와 정기 작업에서도
50개 후보씩 점검한다. 더 남은 경우 다음 주기에서 이어서 검사한다.
웹 서버에서 실행한 정리는 메모리 세션·오버레이 연결·로컬 자동화 음원 폴더도 정리한다.
별도 CLI도 DB·그림 객체와 업로드한 자동화 음원 폴더를 정리한다. 웹 서버의 메모리
세션·연결은 CLI에서 정리할 수 없으므로 운영 서버 재시작 후 캐시를 갱신해야 한다.

## 로컬 음원과 실패 처리

CLI는 계정 삭제 성공 후 `onDeleted`에서 공용 함수
`deleteAccountAutomationSoundFiles(owner)`를 실행한다. dry-run은 파일을 삭제하지 않는다.
저장 경로는 서버와 동일하게 `AUTOMATION_USER_FILE_ROOT` 환경변수를 사용하며,
미설정 시 현재 작업 폴더의 `server/user-files/automation`이다. 실제 업로드 저장소가
마운트된 서버에서, 웹 서버와 같은 작업 폴더·환경변수로 실행해야 한다. 다른 호스트의
파일은 삭제하지 못한다. 대상은 `sha256(owner).slice(0, 32)/sounds`뿐이다.
개인 폴더의 다른 파일이나 다른 계정 폴더는 삭제하지 않는다.

절대 경로 포함 관계를 검사하며, 계정 폴더 또는 `sounds`가 심볼릭 링크·정션이면
삭제를 거부한다. 설정된 저장소 루트의 링크는 실제 경로로 해석한다. 저장소는
신뢰할 수 있는 서버 관리자가 관리해야 한다. 폴더가 이미 없으면 정리 성공으로 처리한다.

결과의 `deleted`는 DB에서 삭제된 계정 수이며, `databaseFailed`와
`soundDirectoriesFailed`는 각각 DB/계정 정리와 로컬 음원 정리 실패 건수다.
`soundDirectoriesCleaned`에는 이미 폴더가 없었던 계정도 포함한다.
`failed`는 이 실패들과 치명적 조회·종료 오류의 합계다. 파일 오류가 발생해도 나머지
계정을 계속 처리하고, 한 건이라도 실패하면 종료 코드 1을 반환한다.
배치별 `soundFailures`는 실패한 폴더의 `ownerKey`와 오류 코드만 기록한다.
원본 예외 메시지·파일 절대 경로·DB 연결 문자열·인증정보는 출력하지 않는다.

DB 삭제가 완료된 계정은 이후 후보 조회에 나타나지 않는다. 따라서 CLI 재실행이나
정기 스케줄러가 해당 계정의 남은 음원을 자동으로 다시 삭제하지 않는다.
실패 배치 로그의 `ownerKey`를 보관하고 권한·마운트·링크 문제를 해결한 뒤,
관리자가 해당 저장소의 `<ownerKey>/sounds`를 확인하여 별도로 정리해야 한다.
원래 계정 ID를 안전하게 보관한 경우 같은 공용 함수를 다시 호출할 수 있다.
현재는 파일 삭제 재시도를 영속 큐에 저장하지 않는다.

서버의 연결 해제·정기 정리와 CLI는 동일한 로컬 파일 삭제 함수를 사용한다.

## 검증 범위

`npm run test:accounts`는 연결 유무, 구형 연결 보호, 생성 유예, 조회 오류,
기본 dry-run, 대상 재검사, 인증 갱신 경쟁, 파일 정리와 CLI 오류 집계를 확인한다.
`ARUBOT_TEST_PGLITE_MODULE`을 지정하면
실제 삭제 SQL의 세션 정리, 다른 계정의 재사용 플랫폼 ID 보존, 실패 롤백도 실행한다.

2026-10-13 작업 환경에서는 설정된 `127.0.0.1` DB가 `ECONNREFUSED`를 반환했다.
따라서 운영 계정 수 조회 및 기존 계정 일괄 삭제는 수행하지 못했다.
